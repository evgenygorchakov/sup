# test

Три уровня проверок, от самого дешёвого к самому дорогому. Уровень — это верхний каталог,
фича — подкаталог или файл внутри него.

| Уровень | Что запускается по-настоящему | Чем запускать | Сколько идёт |
| --- | --- | --- | --- |
| `unit/` | только модуль, никаких провайдеров и терминала | `node test/run.ts` | секунды |
| `stub/` | настоящий цикл хода `src/agent.ts` на провайдере-заглушке | `node test/run.ts` | секунды |
| `live/` | настоящий `sup` в псевдотерминале + настоящая Ollama из `.env` | `python3 test/run.py` | десятки минут |

```
test/
  run.ts               node test/run.ts [фильтр]   — уровни unit/ и stub/
  run.py               python3 test/run.py [фильтр] — уровень live/
  lib/check.ts         общий check()/done() для node-проверок
  lib/drive.py         движок сценариев: псевдотерминал, шаги, проверки
  unit/plan.ts                 \
  unit/thinking.ts              \
  stub/plan-turn.ts              > проверки, названные по фиче
  stub/plan-journal.ts          /
  stub/plan-investigation.ts   /
  live/_selftest/      самопроверка движка (идёт первой: «_» сортируется раньше букв)
  live/plan/           01-smoke … 08-toggle
  live/ask-user/       01-answer … 03-refused
  fixtures/            эталонные состояния песочницы + echo-bot.py
  sandbox/             рабочий каталог живых прогонов, перезаписывается; в git не нужен
  logs/                вывод последнего прогона каждого сценария, с заголовком-шапкой
```

Проверка называется по своему пути: `test/unit/plan.ts` — это `unit/plan`,
`test/live/plan/07-sticky.json` — это `plan/07-sticky`. Этим же именем работает фильтр
(`node test/run.ts plan`, `python3 test/run.py sticky`) и называется лог.

Новая фича добавляется тремя файлами на тех же местах: `unit/<фича>.ts`, `stub/<фича>-*.ts`,
`live/<фича>/NN-*.json`. Раннеры находят их сами, регистрировать нигде не нужно.

## node-проверки

```
node test/run.ts                # всё
node test/run.ts plan           # только те, в чьё имя входит аргумент
node test/run.ts --list         # что вообще есть
node test/unit/plan.ts          # один файл, напрямую
```

Каждый файл — отдельный процесс: они делают `chdir` и правят `process.env` до импорта `src`,
так что в одном процессе им не ужиться. Внутри — `check(имя, факт, ожидание)` из `lib/check.ts`
и `done()` в конце; код возврата и есть вердикт.

## Живые сценарии

```
python3 test/run.py                 # все сценарии подряд
python3 test/run.py sticky 01       # только те, в чьё имя входит аргумент
python3 test/run.py --list          # что вообще есть
python3 test/run.py --quiet         # без вывода псевдотерминала, только итог
python3 test/lib/drive.py test/live/plan/01-smoke.json   # один сценарий, подробно
```

Сценарии идут строго по очереди — у них общая песочница `test/sandbox`. Планирование на `qwen3.8:latest`
занимает 2–8 минут, так что полный прогон — это перерыв на кофе, а не хук перед коммитом; на лёгкой
модели быстрее.

Эталонная модель набора — `qwen3.8:latest` из `.env`. Перебить её можно переменной окружения,
она доходит до `sup` как есть:

```
MODEL=<модель> python3 test/run.py plan
```

Раннер печатает модель в шапке прогона, и каждый лог начинается со строки
`Provider: … · Model: …`: результаты сравнимы только с прогоном на той же модели. Таймауты шагов
рассчитаны на медленную модель — на быстрой они просто не выбираются.

Учти, чем именно рискуешь на лёгкой модели: `02-approve` и `03-auto` утверждают содержимое файлов
после одобренного плана, то есть проверяют заодно и модель. Проверено на `gemma4:latest` (9.6GB):
она переформатировала отступы в аргументе `find` (4 пробела вместо 2 в файле), `edit_file` не нашёл
подстроку, и модель десять раз повторила тот же вызов до стоп-крана по одинаковым батчам — оба
сценария красные при полностью исправном харнессе. На `qwen3.8:latest` те же сценарии зелёные.

Заглушек нет: поднимается настоящий `sup`, он ходит в настоящую Ollama из `.env`. Поэтому
сценарий проверяет то, что делает харнесс — заголовки tool-вызовов, уведомления, файлы,
журнал, — а не формулировки модели. Утверждения вида «модель ответила словом X» будут флаковать.

### Формат сценария

```jsonc
{
  "description": "строка для --list",   // имя берётся из пути, в файле его нет
  "fixture": "calc",            // test/fixtures/calc → test/sandbox перед запуском;
                                // без этого ключа песочница достаётся от предыдущего сценария
  "cwd": "test/sandbox",        // необязательно, пути считаются от корня репозитория
  "cmd": ["sup"], "args": [],   // необязательно
  "env": {"USE_PLAN_MODE": "false"},   // переменные окружения перебивают .env
  "drain": 30,                  // сколько секунд дочитывать вывод после последнего шага
  "xfail": "TASKS.md #3 — …",   // сценарий обязан падать, пока баг не починен

  "steps": [
    {
      "note": "tool confirmation",
      "expect": "Model wants to run:",       // regex по вычищенному от ANSI выводу
      "absent": "edit_file|write_file",      // не должно встретиться до срабатывания expect
      "timeout": 900,
      "send": "n",                           // что напечатать после совпадения
      "delay": 1,                            // пауза перед вводом
      "enter": true,                         // false — послать без Enter (Shift+Tab и подобное)
      "auto_yes": true                       // отвечать y на [y / n / type feedback], пока ждём
    }
  ],

  "forbid": ["Unhandled"],                   // не должно встретиться нигде в выводе
  "files": {
    "calc.js": {"unchanged": true},          // сравнение с копией из fixture
    "README.md": {"contains": "div", "absent": "TODO"},
    "tmp.js": {"exists": false}
  },
  "journal": {                               // .sup/runs/<последний>/journal.jsonl
    "runs": 1,                               // сколько каталогов прогонов создано
    "types": ["run_start"],                  // точная последовательность типов событий
    "types_present": ["tool_call", "finish"],
    "types_absent": ["clear"],
    "contains": "edit_file", "absent": "секрет"
  }
}
```

`expect` ищется с позиции, на которой остановился предыдущий шаг, поэтому окно шага — это
всё, что напечатано между предыдущим совпадением и текущим; именно по этому окну работает
`absent`. Шаг без `expect` просто печатает `send` — так набирается текст в то же окно,
что и у следующего шага.

**Осторожно с ожиданием промпта.** Паттерн вроде `\[ctx: [0-9]+ / ` или `\n> $` совпадает с
промптом, который печатается сразу после предыдущего шага, и шаг «проходит» преждевременно.
Надёжнее сначала дождаться эха отправленного текста, и только потом — следующего промпта.

### Логи

`test/logs/<фича>/<имя>.log` — вывод последнего прогона этого сценария: кадры спиннера вычищены,
а сверху дописана шапка, потому что лог переживает свой прогон, а соседние сценарии его не трогают:

```
# plan/02-approve · 2026-08-23 20:08 · qwen3.8:latest · FAIL · 37s
#   · file calc.js: expected 'function div' in it
```

Модель берётся из баннера самого `sup`, а не из `MODEL`: та переменная пуста, когда модель
выбирается автоматически, и не имеет смысла для сценариев на `echo-bot.py` (там в шапке
`no model banner`). Без этой строки старый лог с другой модели читается как свежее падение.

### xfail

Сценарий с ключом `xfail` обязан падать: так в наборе живут ещё не починенные пункты
`TASKS.md`. Пока баг на месте — `XFAIL`, набор зелёный. Как только сценарий начал проходить,
раннер печатает `XPASS` и роняет прогон: баг починен, надо снять `xfail`. Сейчас с `xfail`
не помечен ни один сценарий.

### Самопроверка

`live/_selftest/` гоняет не `sup`, а `test/fixtures/echo-bot.py` — CLI со скриптованным выводом.
Ollama ему не нужна, идёт секунду, и он стоит первым в очереди, чтобы движок проверок был
проверен до того, как будут потрачены десятки минут. Негативный сценарий намеренно нарушает
каждый вид проверки и перечисляет в `expect_failures`, какие именно сообщения обязаны
появиться, — это защита от «движок проверок молча ничего не проверяет».
